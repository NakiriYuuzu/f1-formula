## 2026-10-29 — online: sudden latency (congested link, host hitches, hidden host page)

- User report: 「多人連線遇到突然延遲」. Three causes found, each reproduced headless, fixed at the source and measured.
- Congestion (`src/net/host.ts`, `NetTransport.buffered`, loopback `bandwidth` / `setBandwidth`): the host sends ~115 KB/s per guest (snapshots ~3 KB at 30 Hz = 92 KB/s, of which the own car's JSON ~1.5 KB; mirror patches ~5 KB at 5 Hz). When the upload got slower than that (Wi-Fi, another upload, SCTP congestion window after loss), everything queued in the send buffer (the unreliable channel dropped only beyond 256 KB ≈ 3 s) and every message — pings, events — waited behind stale snapshots, also after the link recovered. Now snapshots and mirror patches are due on their cadence but sent only while the link's queued bytes (`bufferedAmount`, both channels) ≤ LINK_BACKLOG 1 KB (retried every step, newest wins); snapshots first, a mirror patch (diff since the last one sent) when the link is clear, or after MIRROR_MAX_WAIT 0.5 s behind queued snapshots but never behind a queued reliable message (8 KB/s link: the reliable queue stays ~one patch; forcing behind patches grew it 16 → 40 KB, ping 3.6 s); sendResult forces it. Measured (400 → 50 KB/s for 3 s, 20 cars): snapshot age at the guest 2.1 s → 0.11 s during, 4.7 s → 0.05 s after, ping 1.8 s → 0.14 s; 13 snapshots / s and a patch every 0.6–0.9 s while congested.
- Host hitches (`src/app/clock.ts` ONLINE_*, SessionRuntime, App.loop `FrameTiming.simDt`): the host dropped any frame time beyond 8 steps (67 ms); its step counter then ran behind the guests' seqs, the playout delay shrank and skipped their inputs (a 36-step stall: own-car corrections 6–23 m). Online sessions (host and guest) now catch a slow frame up over the next frames (≤ 24 steps a frame, ≤ 0.5 s; offline unchanged). Catching up alone was worse (24 m): records arriving while the host stalled looked early (age in steps run) and the delay shrank; the arrival age now adds the steps the host still has to run (`HostCallbacks.owed` = `FixedStepClock.owed(wall time since the last step)`: the backlog plus that frame as the clock keeps them, up to 24 steps + 0.5 s). Measured (a 0.3 s and a 0.5 s host frame in a row, every 5 s, run through the online clock): corrections < 0.3 m, delay unchanged (ages in steps run: 6–24 m; time since the last step only: 17 m; owed capped at 0.5 s: 6.3 m).
- Hidden host page (`src/app/backgroundTicker.ts`, App.syncAway / backgroundFrame, SessionRuntime.setAway): browsers stop requestAnimationFrame in a hidden tab, so the host's race froze for everyone. While an online host's page is hidden a dedicated worker's 60 Hz interval drives its frames (simulate + send, no drawing; main-thread interval fallback); its own car is AI-driven and the session sounds fade; back: 「已回到比賽・離開畫面期間由 AI 代駕」, and the hidden time is not caught up (skipDt).
- Fresh-context adversarial review (2 should-fix, 3 nits, all fixed): forced mirror patches piled up below ~80 kbit/s; the owed steps were capped at 60 while the clock can owe 84 (two long frames in a row); returning mid fast-forward re-enabled the session sound; background frames ignored skipDt; a clock test never reached the backlog cap; unused `snapshotsSent` / `isAway` removed; loopback `outgoing` trimmed on send, UTF-8 length of surrogate pairs.
- Tests: net.congestion (new, 2), net.lag +1 (two long host frames through the real online clock), app.clock (new, 5: catch-up, bounds, owed, background ticker with a worker and without). Not browser-verified; the send policy relies on `bufferedAmount` counting SCTP-queued bytes (libwebrtc does; Firefox updates it early — then it behaves as before).
